Error Handling

Catching runtime errors in Jin with try and catch, raising your own with error(), and re-raising one you have already caught.

try and catch

Some things in a program cannot be known until it runs: a file that is not there, a division by zero, a key that is not in a map. try runs a block and hands any error to a handler:

try {
    let text = read_file("notes.txt")
    print(text)
} catch e {
    print("failed: {e}")
}

Without the try, the same program would stop with a message and an exit code of 1. With it, the error is handled and the program carries on:

$ jin notes.jin
failed: 2:25: read_file() could not read notes.txt: The system cannot find the file specified.

The block after catch runs only when the block after try raised something. If it did not, the catch block is skipped and the program continues after the whole statement.

Note. The catch variable cannot be named after a built-in. catch error { ... } is a type error: catch variable "error" cannot shadow a builtin. Use e, or err, or anything else that is not a built-in name.

The catch variable is a str

Whatever you call it, the catch variable holds the error message as a plain string — the same text the program would have printed if nothing had caught it:

try {
    error("boom")
} catch e {
    print(type(e))
    print(e)
    print(len(e))
    print(e + " (added)")
}
str
2:10: boom
10
2:10: boom (added)

It is a str like any other, so it can be printed, measured, concatenated or put in a map. The message includes the line and column it came from, because that is the same text the program would have ended with.

Careful. The message is text, not a structured error. There is no error type, no error code and no stack to look at — just a string. If you need to react to a particular failure, raise it yourself with error() and match on your own wording.

Raising your own error

error() stops the program with a message you choose. It takes one argument and never returns:

fn divide(a: int, b: int) -> int {
    if b == 0 {
        error("denominator cannot be zero")
    }
    return a / b
}

try {
    print(divide(10, 0))
} catch e {
    print("caught:", e)
}
caught: 3:14: denominator cannot be zero

The argument does not have to be a string. Whatever it is, its printed form becomes the message, so error("bad input: {value}") is a good way to put the details in. error(42) raises the message 42.

Re-raising

Calling error(e) inside a catch block hands the error on to the next handler out. That is how you log a failure in one place and handle it in another:

try {
    try {
        error("disk is full")
    } catch inner {
        print("logging:", inner)
        error(inner)
    }
} catch outer {
    print("handled:", outer)
}
logging: 3:14: disk is full
handled: 3:14: disk is full

The outer handler sees the same message, not a new one, so the original place it came from is not lost.

What can be caught

Everything that stops a running program can be caught. These are the six kinds of thing, and the message each one produces:

What goes wrongThe message
You called error()The text you gave it.
A file operation failedread_file() could not read notes.txt: The system cannot find the file specified.
An array index was out of rangeindex 10 out of range (length 2)
A map key was not therekey "email" is not in the map
A division by zerodivision by zero
A record field was read or written that does not existPoint has no field "z"

One program that catches one of each:

# 1. An error you raise yourself.
try {
    error("something went wrong")
} catch e {
    print("caught:", e)
}

# 2. Division by zero.
try {
    let x = 100 / 0
    print(x)
} catch e {
    print("caught:", e)
}

# 3. An index past the end of an array.
let items = ["first", "second"]
try {
    print(items[10])
} catch e {
    print("caught:", e)
}

# 4. A key that is not in the map.
let user = {"name": "Alice"}
try {
    print(user["email"])
} catch e {
    print("caught:", e)
}

# 5. A file that is not there.
try {
    print(read_file("no-such-file.txt"))
} catch e {
    print("caught:", e)
}

# 6. A record field that is not there.
struct Point {
    x: int,
    y: int
}

fn make() -> any {
    return Point(1, 2)
}

let r = make()
try {
    print(r.z)
} catch e {
    print("caught:", e)
}
caught: 3:10: something went wrong
caught: 10:17: division by zero
caught: 19:16: index 10 out of range (length 2)
caught: 27:15: key "email" is not in the map
caught: 34:20: read_file() could not read no-such-file.txt: The system cannot find the file specified.
caught: 51:12: Point has no field "z"

Note. Built-ins that fail at run time are catchable too, not just the six above. int("abc"), float("x") and slice() with an end past the length all raise errors you can catch, because they are all the same kind of thing.

Errors cross function calls

An error raised deep inside a function travels back up to whichever try is waiting for it. The frames in between are unwound as it goes:

fn divide(a: int, b: int) -> int {
    if b == 0 {
        error("denominator cannot be zero")
    }
    return a / b
}

fn outer() -> int {
    return divide(10, 0)
}

try {
    print(outer())
} catch e {
    print("caught:", e)
}
caught: 3:14: denominator cannot be zero

The same is true for a method:

struct Account {
    balance: int
}

fn (a: Account) withdraw(amount: int) -> int {
    if amount > a.balance {
        error("insufficient funds")
    }
    a.balance = a.balance - amount
    return a.balance
}

let acct = Account(50)
try {
    acct.withdraw(100)
} catch e {
    print("caught:", e)
}
caught: 7:14: insufficient funds

And the same for an imported file. The message names the file the error came from, so you can tell where it was raised:

# util.jin
fn half(n: int) -> int {
    if n < 0 {
        error("negative input")
    }
    return n / 2
}
# main.jin
import "util" as util

try {
    print(util.half(-1))
} catch e {
    print("caught:", e)
}
caught: util.jin:3:14: negative input

Type errors cannot be caught

Everything above is a runtime error: it happened while the program was running, and the program was still there to catch it. A type error is different — it is found before the program starts, so there is nothing running to catch it.

try {
    let x: int = "abc"
    print(x)
} catch e {
    print("caught:", e)
}
$ jin err_type.jin
jin: err_type.jin has type errors:
  2:5: cannot assign str to int variable "x"

The catch block is never reached. The type checker runs first, and if it finds anything it reports it and the program never begins.

Error. try catches runtime errors only. It is not a way to make a type error go away — if a program does not type-check, it does not run, and no amount of try will change that. Put the annotation on the right, or leave it off.

The same is true of syntax errors: the file has to be readable before anything can run. The Type System page lists every check that happens before the program starts.

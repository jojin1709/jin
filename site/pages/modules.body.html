Projects and Imports

How a Jin program is split across files, how one file reaches another's names, and how a folder becomes a project with a jin.toml.

Importing a file

An import statement names another Jin file and gives it a name of its own:

import "utils" as u

The alias is not optional. import "utils" without as is a syntax error, and so is import "utils" as with no name after it:

jin: noalias.jin has syntax errors: 1:8: expected as, got EOF

The alias is required because a bare name from another file is exactly the sort of surprise Jin exists to avoid. u.helper(x) says where helper came from; a plain helper(x) would not.

An import is a top-level statement. Putting one inside a function, an if, a while or a for is a syntax error:

jin: nested.jin has syntax errors: 2:5: 'import' is only allowed at the top level of a file

The path is the file's name without the .jin ending, and it is relative to the file doing the importing:

import "utils" as u             # utils.jin, beside this file
import "lib/math" as math       # lib/math.jin

Note. Importing "lib/math" reaches lib/math.jin. Writing "lib/math.jin" is an error: import "u.jin": leave the .jin off, because a path names a file without it.

What an import brings

Everything at the top level of the imported file is reachable through the alias, and nothing else is.

# utils.jin
let name = "utils"

fn double(n: int) -> int {
    return n * 2
}
# main.jin
import "utils" as u

print(u.double(21))        # 42
print(u.name)              # utils
42
utils

Both a let and a fn at the top level of a file are part of that file's exports, and so is a struct — u.Point is a type you can construct and pass around like any other value.

Names inside a function, or inside any block, stay where they were written. A file's exports are its top-level names, so there is no export keyword to write and nothing to keep in sync.

If the importing file asks for a name the imported file does not have at the top level, the type checker says so before the program runs:

jin: main.jin has type errors:
  2:8: u has no name "hidden"

An alias is a way to reach names, not a value. Printing one is an error:

jin: main.jin has type errors:
  2:7: "u" is a module; write u.<name> to use a name from it

When files run

An import runs the file it names, once, before the importing file's own statements. Files run in dependency order, so a file that imports two files sees both of them ready.

The loader reads each file once and remembers it, so importing the same file from two places — or twice from the same place — still runs it once.

# main.jin
import "a" as a
import "shared" as s1
import "shared" as s2

print("main")
print(s1.x, s2.x)
# a.jin
import "shared" as s
print("a")
# shared.jin
print("shared")
let x = 7
shared
a
main
7 7

shared printed once even though three files import it, and it printed before a, which printed before main. The bytecode VM and the tree-walking interpreter produce exactly this output.

A file's own top-level statements run before the file that imports it gets to its own statements. So a failure inside an imported file — even one raised by a function the importing file calls — is what the program reports:

before
jin: boommod.jin:3:15: division by zero

Import cycles

A cycle is reported rather than hung on. The loader keeps a stack of the files it is reading, and when a file reaches itself it names the whole chain:

jin: import cycle: a.jin -> b.jin -> a.jin

A file that imports itself is a cycle too, with one name in it:

jin: import cycle: selfimp.jin -> selfimp.jin

Import paths

An import path is relative to the file doing the importing, uses / between folders, and cannot leave the folder the importing file is in.

PathWhat happens
"utils"Looks for utils.jin beside the importing file.
"lib/math"Looks for lib/math.jin beside the importing file.
"utils.jin"Rejected: leave the .jin off.
"lib\math"Rejected: use / between folders.
"./utils"Rejected: drop the leading ./.
"../utils"Rejected: an import cannot point outside this file's folder.
"/utils"Rejected: an import path is relative to this file.
"lib//math"Rejected: empty path segment.

A file that cannot be found is reported at the import that caused it:

jin: 1:1: cannot find module "nope"; there is no nope.jin to import

Careful. An import cannot reach out of its own folder, so a file in lib/ cannot import the project's top-level files. Every file can only reach the folder it sits in and the folders below it.

Another file's names are read-only

A file's names belong to that file. From outside, they can be read and called, but not written:

jin: main.jin has type errors:
  2:2: cannot assign to u.a; another file's names are read-only

The file that owns the name can still change it. A counter that lives in another file still counts:

# counter.jin
let count = 0

fn bump() {
    count = count + 1
}
# main.jin
import "counter" as c
c.bump()
c.bump()
print(c.count)          # 2

Alias rules

Because every file's names are kept apart, an alias has to be a name of its own. Three rules are checked before the program runs, at the import that caused the problem.

An alias may not be a name the importing file already declares

jin: 1:1: this file also defines "u", so the name would be ambiguous

This applies to a let, a fn and a struct alike.

An alias may not shadow a built-in

jin: 1:1: "print" is a built-in function; pick another name for the import

An alias may not be reused

Two imports in one file cannot share an alias:

jin: 2:1: "u" is already the name for another import (line 1)

Two different files may use the same alias, though. The alias belongs to the file that wrote it.

A project and its manifest

A folder holding a jin.toml is a project. The manifest is deliberately small — a name, a version, and the file to start from:

# jin.toml
name = "greeting"
version = "1.0.0"
entry = "main.jin"
SettingWhat it meansDefault
nameThe project's name, used in messages.The folder's name.
versionThe project's version, used in messages.0.1.0
entryThe file to run, relative to the project folder.main.jin

Only those three settings are accepted. An unknown one is an error, and so is an entry that does not name a .jin file inside the project folder:

jin: jin.toml:1: unknown setting "deps"
jin: jin.toml:1: expected name = "value"
jin: jin.toml: entry "app.txt": a Jin file ends in .jin
jin: jin.toml: entry "../app.jin": the entry file is inside the project folder

An empty value keeps the default, so a manifest can be as small as a comment.

Note. The entry file is a file inside the project folder. A manifest cannot point outside it.

Starting a project

jin new writes a working project into a new folder:

go build -o jin.exe .
./jin.exe new hello
created hello/
  jin.toml
  main.jin
  greeting.jin

next: cd hello && jin run

The project it writes has two files, joined by an import, so it shows the shape of a project from the first minute:

# hello/main.jin
# Run this with 'jin run' and check it with 'jin check'.

import "greeting" as greeting

let who = args()
if len(who) == 0 {
    print(greeting.hello("world"))
} else {
    print(greeting.hello(who[0]))
}
# hello/greeting.jin
# Names in this file are reached as greeting.<name>.

fn hello(who: str) -> str {
    return "Hello, {who}!"
}

The name has to be usable as a folder name — letters, digits, - and _ — and jin new refuses to write over a folder that already exists.

Running a project

A project can be run by naming its folder, or from anywhere inside it, the way a build tool works. The command walks up from the current folder until it finds a jin.toml.

./jin.exe run examples/greeting
./jin.exe run examples/greeting Jin
cd examples/greeting
../../jin.exe run
../../jin.exe check

Three commands work on a project:

CommandWhat it does
jin runChecks the project, compiles it, and runs it on the bytecode VM.
jin checkType-checks every file the project reaches, and runs nothing.
jin buildChecks and compiles the whole project, and reports what came out.

The shipped examples/greeting project has exactly this shape — two files, joined by an import:

# examples/greeting/main.jin
# A project made of two files, joined by an import.
#
#   jin run examples/greeting
#   jin run examples/greeting -- Jin Jo

import "words" as words

let who = args()
if len(who) == 0 {
    who = ["world"]
}

for name in who {
    print(words.greet(name))
}
# examples/greeting/words.jin
# A file's names are reached as words.<name>, so nothing here can clash with
# a name in the file that imports it.

let greeting = "Hello"

fn greet(name: str) -> str {
    return "{greeting}, {name}!"
}

Running it, and checking it:

./jin.exe run examples/greeting
./jin.exe run examples/greeting Jin
Hello, world!
Hello, Jin!
./jin.exe check examples/greeting
./jin.exe build examples/greeting
greeting 1.0.0: no type errors in 2 file(s)
jin build: greeting 1.0.0
  entry: main.jin
  files: main.jin, words.jin
  code:  116 bytes of bytecode, 8 constants, 3 locals
  ok

Note. jin build is a check-and-compile step, not a step that writes a binary. Jin runs from source, so there is no artefact to keep in step with the source — and no stale binary to go wrong.

Program arguments

args() returns the arguments the program was run with, as an array of strings. Anything after the file or folder name reaches the program:

let who = args()
if len(who) == 0 {
    print("no arguments given")
} else {
    print("hello, {who[0]}")
}
./jin.exe run greet.jin Ada Bo
hello, Ada

A -- before the arguments is allowed and ignored, so a program can be given arguments that look like Jin's own:

./jin.exe run examples/greeting -- Jin Jo
Hello, Jin!
Hello, Jo!

Inside a project, args() works the same way — the arguments come after the project, not before it.

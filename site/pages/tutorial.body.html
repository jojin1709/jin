Getting Started

Build the Jin compiler, run your first program in four steps, and learn how to read the errors Jin gives you before your program ever starts.

What you need

Jin needs exactly one thing: Go 1.21 or newer. Jin itself is written in Go, has no third-party dependencies, and builds offline on a fresh checkout. The CLI, the virtual machine and the standard library are platform-independent, so Windows, Linux and macOS all work.

$ go version
go version go1.26.2 windows/amd64

Note. The Go version is the version of the compiler you build Jin with. It is not something a Jin program needs at run time. Once you have built the binary, you can copy that one file to any machine with the same operating system and architecture and it will run there on its own.

Install it

There are three ways to get jin, and they all give you the same binary.

With Go

If you have Go 1.21 or newer, one command installs it:

$ go install github.com/jojin1709/jin@latest

Go puts the binary in the folder go env GOBIN names, which is $(go env GOPATH)/bin unless you set GOBIN yourself. That folder has to be on your PATH:

$ go env GOBIN
/home/you/go/bin

Note. @latest means the newest tagged release, so this needs a release to exist. A build from source, below, always works.

From a release

If you would rather not have Go on the machine, download the archive for your platform from the releases page, unpack it, and put the jin binary on your PATH. Each archive holds the binary, the licence and the README, along with a checksum to check the download against.

From source

Get the source and build the command-line tool. In the folder that holds the repository:

$ go build -o jin.exe .
$ ./jin.exe --version
jin dev

On Linux and macOS the same command gives you jin instead of jin.exe:

$ go build -o jin .
$ ./jin --version
jin dev

A build from source says dev, because it has no version stamped into it. A released binary says the version it was built as, such as jin 0.10.1.

The build prints nothing when it works. If you want to see that the tests pass as well, they run in a few seconds:

$ go test ./...
ok  	github.com/jojin1709/jin	2.478s

The number at the end is how long the suite took. There are 406 test cases in it.

The rest of this page writes the command as jin. On Windows that means jin.exe, unless you rename the file — putting the folder it is in on your PATH is the tidiest way to work.

Every other jin subcommand — run, check, build, new, compile, parse, tokens — is described on the Command Line page.

Run a program

Make a file called hello.jin:

print("Hello, world!")

Then run it:

$ jin hello.jin
Hello, world!

There is no main function and no boilerplate. A Jin file is the program: the statements at the top level run from top to bottom, and then it ends.

Anything you write after the file name is passed to the program, where args() returns it as an array of strings:

$ jin hello.jin Ada
Hello, world!

Your first program, in four steps

Step 1 — say something

print("Hello, world!")
Hello, world!

print writes its arguments separated by a space, then a newline. It returns nothing, so there is no return to write.

Step 2 — hold a value

let name = "Jin"
let count = 3

print("Hello, {name}!")
print("You have {count} new messages.")
Hello, Jin!
You have 3 new messages.

let declares a name. The {name} inside a string is an interpolation: the value of name is put into the text. Write {{ if you want a literal brace.

Note. A name that has not been declared cannot be assigned to. count = 4 works once count exists; counter = 4 on its own is a type error, not a new global. That is on purpose — a typo should stop you, not quietly create a variable.

Step 3 — do it again

fn greet(who: str) -> str {
    return "Hello, {who}!"
}

print(greet("Jin"))
Hello, Jin!

fn declares a function. The names in the brackets are its parameters, the type after the bracket is what it returns, and the body is a braced block. Type annotations are optional — leaving them off changes nothing — but writing them means the mistake is found before the program runs.

Step 4 — repeat it

fn greet(who: str) -> str {
    return "Hello, {who}!"
}

for name in ["Ada", "Grace", "Alan"] {
    print(greet(name))
}
Hello, Ada!
Hello, Grace!
Hello, Alan!

for walks over an array, a string or a range. The name after for is a fresh binding on every pass, so a function made inside the loop keeps that pass's value.

The REPL

Run jin with no arguments outside a project and you get an interactive session. State persists between lines, and the value of the last expression on a line is printed back to you.

$ jin
Jin 0.10.0 (stage 10: input, functional built-ins, multi-line strings, named records)
Type Jin code and press Enter. 'exit' or Ctrl+D quits.
'clear' discards a half-typed block.
jin> let x = 5
5
jin> x + 1
6
jin> print("hello from the repl")
hello from the repl
jin> fn double(n) { n * 2 }
jin> double(21)
42
jin> exit

Type exit, or press Ctrl+D, to leave. A line that does not type-check is reported and the session carries on, so a mistake does not cost you the whole session.

Running a project

A folder holding a jin.toml is a project, and a folder can be run the same way a file can:

$ jin run examples/greeting
Hello, world!
$ jin run examples/greeting -- Jin Jo
Hello, Jin!
Hello, Jo!

You do not have to write the folder by hand. jin new starts one for you:

$ jin new hello
created hello/
  jin.toml
  main.jin
  greeting.jin

next: cd hello && jin run

From inside that folder, jin run runs the project and jin check type-checks every file it reaches:

$ cd hello
$ jin run
Hello, world!
$ jin check
hello 0.1.0: no type errors in 2 file(s)

Splitting a program across files, and what an import alias does, is covered on the Projects and Imports page.

Reading Jin's error messages

Jin checks a program before it runs it, so most mistakes are reported up front with the line and column they came from. There are three kinds of message, and each one has its own shape.

Type errors — the program never starts

These are found by the type checker. Every one of them is listed at once, so one run tells you about all of them. Given this file:

fn area(w: int, h: int) -> int {
    return w * h
}

let width: int = 3
let height = "4"

print(area(width, height))
print(area(width))
print(1 + "x")
if width {
    print("wide")
}
print(mystery)
$ jin badtypes.jin
jin: badtypes.jin has type errors:
  8:11: argument 2: cannot use str where int is expected
  9:11: area() expects 2 argument(s), got 1
  10:9: cannot add int and str
  11:1: condition must be a bool, got int
  14:7: undefined variable "mystery"

Each line is line:column: message. The column is where the offending expression starts, counting from 1. The exit code is 1, and nothing was printed to standard output — the program did not run.

To see the same list without running anything, use jin check. It is the same check, so the answer is the same:

$ jin check badtypes.jin
jin: badtypes.jin has type errors:
  8:11: argument 2: cannot use str where int is expected
  9:11: area() expects 2 argument(s), got 1
  10:9: cannot add int and str
  11:1: condition must be a bool, got int
  14:7: undefined variable "mystery"

Syntax errors — the file could not be read

When the parser cannot make sense of the text, the errors come back on one line, separated by ;. Given a file with a stray closing brace:

let x = 1
print("hello")
}
$ jin extra.jin
jin: extra.jin has syntax errors: 3:1: unexpected token "}"

Read these from the left. The first message is the one that usually explains the rest: once the parser loses the shape of the file, everything after it is nonsense.

Note. A block that is never closed is reported: missing '}' at the end of the file. A missing brace used to be accepted quietly, and it swallowed the rest of the file into the block above it.

Runtime errors — the program started and then stopped

Everything the type checker cannot know about — a file that is not there, a division by zero — happens while the program runs. The message points at the line that raised it:

fn half(n: int) -> int {
    return n / 0
}

print(half(10))
$ jin boom.jin
jin: 2:14: division by zero

Here the shape is line:column: message with no file name, because there is only one file. The exit code is 1.

These runtime errors can be caught with try and catch, which is the subject of the Error Handling page. Type errors cannot — they happen before the program starts, so there is nothing running to catch them.

The shape of a Jin file

# A comment starts with a hash.

fn greet(who: str) -> str {
    return "Hello, {who}!"
}

# A ';' is optional between statements.
let a = 1; let b = 2
print(a + b)

print(greet("Jin"))
3
Hello, Jin!
  • Comments start with # and run to the end of the line.
  • Statements sit at the top level or inside a { } block. A ; between them is optional; a newline is not a statement separator, because Jin uses braces and not indentation.
  • let declares a name. A name may only be assigned to after it has been declared.
  • fn declares a function. It has to be written before a top-level statement calls it — the declaration is what fills the name in. Two functions may call each other in either order, because those names are resolved before either body runs.
  • struct declares a record type, and import brings another file's names in behind an alias. Both belong at the top level of a file.
  • There is no main. The file is the program.

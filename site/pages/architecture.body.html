Architecture

How a Jin program becomes running bytecode: the lexer, the parser, the module loader, the type checker, the compiler and the virtual machine — and the tree-walking interpreter kept beside it.

The pipeline

Jin is written as a pipeline. Source text goes in one end and running values come out the other, and each stage has one job.

source text
   |  lexer.go        -> tokens
   v
tokens
   |  parser.go       -> syntax tree
   v
syntax tree            (ast.go)
   |  module.go       -> the file plus everything it imports
   v
one whole program
   |  typechecker.go  -> type errors, or a clean bill of health
   v
one whole program
   |  compiler.go     -> bytecode
   v
bytecode               (code.go)
   |  vm.go           -> result
   v
values                 (object.go, record.go, builtins.go)

alternate back end
one whole program
   |  interpreter.go  -> result       (jin interpret)
   v
values                 (object.go, environment.go, builtins.go)

The stages, in order:

  1. Lexer (lexer.go) turns source text into tokens, each one carrying the line and column it came from.
  2. Parser (parser.go) turns the tokens into a syntax tree, using a precedence table so 1 + 2 * 3 groups the way it reads.
  3. Module loader (module.go) reads the file and everything it imports, resolves the import paths and aliases, refuses cycles, and hands the whole program over as one unit.
  4. Type checker (typechecker.go) walks the tree and reports every problem it can find, or a clean bill of health.
  5. Compiler (compiler.go) turns the tree into bytecode, resolving every name to a slot on the way.
  6. Bytecode (code.go) is the finished instruction stream, with its constants, its positions and its local slots.
  7. VM (vm.go) runs the bytecode on a value stack with a stack of call frames.

The tree-walking interpreter (interpreter.go) is an alternate back end for the same tree. It is slower, and that is the point of keeping it: the test suite runs every program on both engines and demands byte-identical output, so the two cannot drift apart without a test noticing.

Note. Each stage is available on its own from the command line: jin tokens, jin parse, jin check, jin compile. You can watch a program being translated one layer at a time.

The bytecode is readable. jin compile prints the constants and then the instruction stream:

How names resolve to slots

The compiler resolves every name before the program runs. By the time the VM sees a name, it is no longer a name — it is a number saying where the value lives.

There are four places a name can live, and each has its own pair of opcodes:

Where the name livesScopeReadWrite
A global slot, for a top-level let, fn or structGlobalScopeOpGetGlobalOpSetGlobal
A slot in the current call frame, for a parameter or a localLocalScopeOpGetLocalOpSetLocal
A captured variable, held by the enclosing function's closureFreeScopeOpGetFreeOpSetFree
A built-in functionBuiltinScopeOpGetBuiltin—

The symbol table (symboltable.go) hands out those slots. A name at the top level of the file you ran is a global; a name anywhere else is a slot in the frame. Blocks nest: leaving a block puts back whatever it shadowed. Slots handed out inside a block are not reclaimed, because a frame is sized by the highest slot ever used, and keeping the counter high is what makes the size right.

A name that belongs to an enclosing function becomes a captured variable. The compiler records where it came from — a local slot of the enclosing frame, or an entry in the enclosing closure's free list — and the closure is built with exactly those captures.

A name that is in none of those places is an error, not a runtime surprise. The type checker catches it before the program starts:

jin: main.jin has type errors:
  1:7: undefined variable "y"

Note. This is why jin check and jin compile catch different classes of mistake: the checker works on types and on the names it can see statically, while the compiler works on slots, closures and the instructions themselves.

Every instruction knows where it came from

The compiler records a source position for every byte it emits, in a table that sits alongside the instruction stream. Each entry holds a line, a column, and the file the code came from.

When the VM raises an error it looks up the position of the instruction that was running, and builds the message from it. The tree-walking back end does the same thing from the tree, so both engines print the same message for the same mistake.

The file name is left out when the code came from the file you ran — there is only one of that, so the message stays plain:

jin: 3:5: division by zero

When the code came from an imported file, the instruction carries that file's name, which is its path relative to the file you ran:

# utils.jin
# A deliberate mistake, to show where an error points.
100 / 0
# main.jin
import "utils" as u
print("never reached")
jin: utils.jin:3:5: division by zero

The same message comes out of both back ends:

./jin.exe run main.jin
./jin.exe interpret main.jin
jin: utils.jin:3:5: division by zero
jin: utils.jin:3:5: division by zero

Kept in one place

Two pieces of logic live in exactly one place, so the back ends cannot drift apart.

indexInto and setInto in vm.go do every indexed read and write, and iterateValues decides what a for loop walks. The interpreter calls all three, which is why an error message about a map key is the same whichever engine you run.

  • indexInto(container, index) reads container[index]: a map lookup, an array element or a character of a string.
  • setInto(container, index, value) writes container[index] = value.
  • iterateValues(obj) turns a collection into the values a loop walks: an array stays as it is, a string becomes its characters, and a map becomes its keys in the order they were added.

A missing map key is an error on both engines, not a quiet nil:

2:8: key "nope" is not in the map

The same idea runs through the record code: getField and setField in record.go are the only places that read or write a field, and they build the message for a name a record does not have. The type checker builds the same text, so a mistake is caught before the program runs when it can be, and reported the same way when it cannot.

How closures use cells

A captured variable is the variable, not a snapshot of it. Two functions written side by side see each other's writes, and each pass of a loop gets its own binding.

The VM does this with cells. Each captured local gets one cell, and every closure that captured it shares that same cell — which is where the sharing comes from.

  • While the frame that owns the variable is still running, the cell points straight at that frame's stack slot. An ordinary read or write of the local is therefore seen by every closure holding it.
  • When the scope ends — the block closes, or the frame returns — the value is copied out of the slot and the cell is closed. That is what lets a closure outlive the call that made it.
  • A second closure capturing the same slot gets the same cell. That is what makes sibling closures see each other's writes.

In the code, capture(slot) in vm.go finds or creates the cell for a slot, closeCells(from) closes every cell at or above a slot, and the OpCloseUpvalues instruction closes the cells a block owns. The cell itself lives in object.go, next to the closure it belongs to.

The tree-walking back end reaches the same semantics a different way: it hands every function a pointer to the environment it was written in, so the captured variable is shared by construction. Both engines run the same differential corpus, so the two cannot disagree about what a capture means.

The differential corpus

The centrepiece of the test suite is a corpus of programs that is run on both back ends, and the two results have to match exactly — including the text of any error.

Two independent implementations agreeing is a far stronger correctness signal than either one passing on its own.

What the corpus covers:

  • 96 programs in vm_test.go, from integer arithmetic and operator precedence through closures, records, maps and string interpolation. Each one must produce its expected output on the VM and on the interpreter.
  • 31 error programs that must fail on both engines. The wording is pinned, so a bug cannot make both engines wrong in the same way, and the two messages are compared to each other byte for byte.
  • Every file in examples/, run on both engines and compared.
  • Every project under test: the tests write real files into a temporary folder and require both back ends to agree on what the whole project prints, and on where it fails when a module, an alias or an import path is wrong.

Error programs take the same route as working ones, which is what keeps the two engines honest about their messages rather than merely compatible.

The whole suite is 396 test cases, all passing:

go test ./...
go vet ./...
gofmt -l .
ok  	jin	4.589s

Performance

Naive fib(30), wall clock including start-up, compile and type-check, measured on the machine the project describes (Windows, Go 1.26, CPython 3.14, prebuilt binary, median of five runs):

EngineTime
jin run (bytecode VM)~0.15 s
jin interpret (tree walker)~0.93 s
CPython 3.14, same program~0.14 s

So the VM is roughly six times faster than Jin's own tree-walking back end, and it is level with CPython on a call-heavy benchmark. The exact figures depend on the machine; the ratio is the thing to take away.

The VM keeps that lead by doing the work before the program starts, and by not doing it again:

  • Names are resolved to slots before execution, so there is no name lookup at run time.
  • Small integers, booleans and nil are pooled instead of allocated on every step.
  • Call frames are reused, so a call allocates nothing.
  • The common arithmetic cases are handled without building any object that gets thrown away.

Getting clearly past CPython would need unboxed stack slots and inline caches, which are a later stage's work.

Type System

Jin's type annotations are optional, and they are checked before your program runs. This page is the reference for what the checker accepts, what it refuses, and the exact words it uses when it refuses.

Annotations are optional

You never have to write a type. When you do write one, Jin enforces it before the program starts, so a mistake is found up front instead of halfway through a loop.

fn area(w: int, h: int) -> int {
    return w * h
}

let width: int = 4
let height = 3

print(area(width, height))
12

The same program with the wrong types does not run at all:

fn area(w: int, h: int) -> int {
    return w * h
}

let width: int = 3
let height = "4"

print(area(width, height))
jin: area.jin has type errors:
  8:11: argument 2: cannot use str where int is expected

The annotation names

These are the type names the checker knows. Anything else is refused with unknown type "...".

NameWhat it accepts
intA whole number.
floatA decimal number.
strText.
booltrue or false.
nilThe absence of a value.
arrayA list. The elements are not checked.
mapA map. The values are not checked.
anyAnything. Nothing is checked.

A bare array or map leaves the contents alone, which is usually what you want, because a map holding a name and an age at once is normal:

let mixed: array = [1, "two"]
let person: map = {"name": "Ada", "age": 36}
print(mixed)
print(person)
[1, "two"]
{"name": "Ada", "age": 36}

The name of a record declared in the file also works as a type, so let p: Point = Point(1, 2) is checked against the record's own fields.

Note. nil is a keyword in Jin, and it is also the name of a type, so the parser accepts it as an annotation: let x: nil = nil is a name that can only ever hold nil.

What is left alone

A function parameter with no annotation is any, and a function with no return annotation is not return-checked at all. Plain scripts therefore keep working exactly as they always did.

fn double(value) {
    return value * 2
}
print(double(21))
42

A parameter of type any may be given any value at all, and it may be reassigned to anything:

fn f(v) { v = "text"; return v }
print(f(1))
text

An unannotated let still takes the type of its value

This is the one place where an unannotated name is not simply any. A let with no annotation takes the kind of the value it is given, so the name is still checked afterwards:

let x = 1
x = "text"
jin: x.jin has type errors:
  2:3: cannot assign str to int variable "x"

Give the name the annotation any if you want it to hold anything later.

let x: any = 1
x = "text"
print(x)
text

Checking before the program runs

jin check type-checks a file and reports the problems without running anything.

go build -o jin.exe .
./jin.exe check examples/types.jin
examples/types.jin: no type errors

Running a file checks it first. A program with a type error never starts, so there is no half-finished run and no output to clean up.

let x: int = "text"
print("never")
./jin.exe broken.jin
jin: broken.jin has type errors:
  1:1: cannot assign str to int variable "x"

Every problem in the file is reported at once, and they come out in the order they appear, each with the line and column it came from.

Note. Jin prints the name of the file you gave it, so the examples on this page name the file they belong to. The wording of each message is the same whatever the file is called.

A file with several problems

Every problem is reported, not just the first one.

fn area(w: int, h: int) -> int {
    return w * h
}

let width: int = 3
let height = "4"

print(area(width, height))
print(area(width))
print(1 + "x")
if width { print("hi") }
for n in 42 { print(n) }
let bad: int = "text"
print(area(width, "three"))
jin: area.jin has type errors:
  8:11: argument 2: cannot use str where int is expected
  9:11: area() expects 2 argument(s), got 1
  10:9: cannot add int and str
  11:1: condition must be a bool, got int
  12:1: cannot loop over int
  13:1: cannot assign str to int variable "bad"
  14:11: argument 2: cannot use str where int is expected

Flow-sensitive checking

The checker follows the order of the program. It knows what each name holds at each point, and it knows which names exist there.

A function may use a name declared further down

Function bodies are checked after the whole file has been read, so a helper at the top can use a variable that is declared below it:

fn shout() { print(upper(message)) }
let message = "hi"
shout()
HI

Top-level code does not get that allowance. It runs in order, so it has to meet a name before it uses it:

print(message)
let message = "hi"
jin: message.jin has type errors:
  1:7: undefined variable "message"

A block's names stay in the block

if true {
    let hidden = 1
    print(hidden)
}
print(hidden)
jin: block.jin has type errors:
  5:7: undefined variable "hidden"

Two functions in the same body can call each other

Both names are known before either body is checked, so the order they are written in does not matter:

fn outer() {
    fn a(n) {
        if n <= 0 { return "a" }
        return b(n - 1)
    }
    fn b(n) {
        if n <= 0 { return "b" }
        return a(n - 1)
    }
    return a(5)
}
print(outer())
b

A local declared with let still has to come first, and the allowance stops at the block the functions were declared in:

if true {
    fn hidden() { return 1 }
}
hidden()
jin: scope.jin has type errors:
  4:1: undefined variable "hidden"

Shadowing a built-in

A local or a global may take a built-in's name. The name then means the variable, not the built-in, and the checker knows that: it stops checking the call as a built-in call and checks it as a call of your own function.

let len = 3
print(len)

fn width(items) {
    let len = "hidden"
    return len
}
print(width([]))
3
hidden

Calling the shadowing name is then a call of an int, and the checker says so:

let len = 3
print(len(5))
jin: shadow.jin has type errors:
  2:10: int is not callable

Where nothing shadows it, the built-in's own checks still apply:

print(len(5))
jin: len.jin has type errors:
  1:10: len() expects str, array or map, got int

Error. A catch variable may not shadow a built-in. catch len is refused with catch variable "len" cannot shadow a builtin.

Type errors cannot be caught at run time

A type error is found before the program starts, so there is nothing running that could catch it. try and catch handle run-time errors only.

try {
    let x: int = "text"
    print("this never runs")
} catch e {
    print("caught: {e}")
}
jin: caught.jin has type errors:
  2:5: cannot assign str to int variable "x"

The program does not run, so the block inside the try never executes and the catch never runs either.

A run-time error is a different thing, and try does catch it:

try {
    let x = 1 / 0
} catch e {
    print("caught: {e}")
}
caught: 2:15: division by zero

So there are two kinds of failure in Jin, and they are never mixed up: a type error stops the program before it starts, and a run-time error stops it while it runs, where a handler can pick it up. Error handling is covered in Error Handling.

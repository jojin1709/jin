Status and Roadmap

What Jin can do today, what it cannot do yet, the nine rules it is built around, and what comes after stage 10.

The stages so far

Jin was built one stage at a time, and each stage was proved against the ones around it. All ten stages are finished, together with the work on closures that went with them.

  • Stage 1: lexer. Source text to tokens, with the line and column of every token tracked so errors can point at the right place.
  • Stage 2: parser. Tokens to a syntax tree, using a precedence table, with every syntax error reported with a position.
  • Stage 3: interpreter. A tree-walking interpreter, kept ever since as the reference implementation the VM is checked against.
  • Stage 4: type checker. Optional annotations, enforced before the program runs: argument counts, mismatched types, non-bool conditions, bad indexing, misplaced break and return.
  • Stage 5: bytecode compiler and VM. A stack machine with a pooled constant table, pre-allocated frame slots and reused call frames, running names resolved to slots.
  • Stage 6: standard library. The built-in functions: strings, numbers, lists, maps, files and the functional ones, shared by both back ends.
  • Closures. Shared captures, a fresh binding on every pass of a loop, and mutual recursion between nested functions.
  • Stage 7: package manager and CLI. Imports, projects, jin new, jin build and args().
  • Stage 8: records. User-defined struct types, constructors, receiver methods (fn (p: Point)), dotted field access and mutation.
  • Stage 9: error handling. try / catch statements, catchable runtime errors and error(), and re-raising across handler frames.
  • Stage 10: real programs. Terminal input (input, read_all_stdin), multi-line strings ("""), higher-order built-ins (map, filter, reduce, any, all, sort_by, find_index), and named record construction (Point{x: 1, y: 2}).

The version string says which stage the build is at:

./jin.exe --version
Jin 0.10.0 (stage 10: input, functional built-ins, multi-line strings, named records)

The design rules

Nine rules decide what Jin does and does not do. They are the reason the language looks the way it does.

  1. Braces, not invisible whitespace. No broken programs because of a stray tab.
  2. One obvious way to do things. No decorators, no metaclasses, no dunder magic.
  3. No silent type mixing. 1 + 1.5 is an error, not a surprise. Convert with int() or float().
  4. Conditions must be bool. if 1 { } is rejected instead of quietly being truthy.
  5. No accidental globals. Assigning to a name that was never declared is an error.
  6. A missing key is an error. m["nope"] is not quietly nil; ask with has(m, "nope").
  7. A captured variable is shared, not copied. Two functions written side by side see each other's writes to it, and each pass of a loop gets its own binding rather than the last value the loop reached.
  8. Fast by default. Source compiles to bytecode and runs on a stack VM. The tree-walking interpreter is still there for cross-checking, but it is not what run uses.
  9. A file's names belong to that file. Nothing in another file is in scope until you import it and name it through the alias, and another file's names are read-only from the outside.

What is in

Everything Jin can do today, listed honestly.

Records, with named and positional construction. Try / catch error handling. Terminal input (input, read_all_stdin). Multi-line strings ("""). Higher-order functions (map, filter, reduce, any, all, sort_by, find_index). Maps. sort, reverse and slice. String and number helpers. error. File I/O.

examples/records.jin, examples/errors.jin, examples/functional.jin, examples/input.jin, examples/collections.jin and examples/files.jin exercise all of it.

Multi-file programs are in too. import "utils" as u puts another file's top-level names behind an alias, a folder with a jin.toml is a project, and jin new, jin build, jin check and jin run work on one. examples/greeting is a two-file project.

And the whole thing runs on two engines — a bytecode VM and a tree-walking interpreter — which the test suite forces to agree, byte for byte, on every program, every error message and every project.

The rest of the language is written down on the other pages: the language tour for the syntax, type system for the checks that run before your program starts, records and methods, error handling, built-ins, projects and imports and the command line.

What is not in

Stated plainly, because a list of what a language cannot do yet is worth more than a list of what it can.

  • No remote packages. Imports are files beside the one that imports them; there is no registry, no download step, and no lock file, because there is nothing to fetch yet. A project is a folder and nothing else.
  • No compiled output. jin build checks and compiles a project and reports what came out, but the result is not written to disk, because Jin runs from source and a stale binary is worse than no binary.
  • No finally blocks, no custom error types, and no try as an expression. Catch blocks receive a str error message.
  • No default field values, no inheritance or interfaces.

Careful. That list is honest, but it is not exhaustive. A few more things the language genuinely does not have today:

  • No switch or match. if / else if is the only branching there is.
  • No overflow checking on integers. They are 64-bit and wrap around silently: 9223372036854775807 + 1 is -9223372036854775808, with no error.
  • No float infinity or NaN. 1.0 / 0.0 is a division by zero error rather than an infinity.
  • No JSON, no regular expressions, and no date or time in the standard library.
  • No way out of the project folder. An import path cannot point outside the folder of the file that writes it, so a project cannot reach a shared library sitting next to it.
  • No formatter, no test runner and no language server yet. gofmt has no Jin equivalent, and an editor cannot ask Jin what a name means.
  • Calls stop at 1024 frames deep. A program that recurses further than that is stopped with an error rather than a crash.

The roadmap

Stage 11 — remote packages

A registry and a versioned lock file, so import "json" as json can pull a package instead of a folder. The loader in module.go is where that lands: it already decides what a path means, what a project is, and how files depend on each other.

A formatter

jin fmt, so that a Jin file can be brought into one shape the way gofmt brings a Go file into one. A language people write in needs a way to settle an argument about spacing without an argument.

A test runner

jin test, so that a Jin program can test itself without leaving the language.

Later — a faster VM

Unboxed stack slots and inline caches, to move clearly ahead of CPython rather than alongside it. Today the VM is roughly six times faster than Jin's own tree-walking back end and level with CPython on a call-heavy benchmark; those two changes are what would change that.

That is the whole of the stated plan. Anything not listed above is not promised.

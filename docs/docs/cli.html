The commands at a glance

CommandWhat it does
jin <file.jin> [args]Compile and run a program on the bytecode VM. The short form of jin run.
jin run [file|folder] [args]Run a program, or a whole project, on the bytecode VM.
jin interpret [file|folder] [args]Run the same program on the tree-walking reference interpreter.
jin check [file|folder]Type-check without running anything.
jin build [folder]Check and compile a whole project, and report what came out.
jin new <name>Start a project in <name>/.
jin compile <file>Print the bytecode instead of running it.
jin parse <file>Print the syntax tree instead of running it.
jin tokens <file>Print the raw token stream.
jinRun the project you are in, or start the REPL.
jin --versionPrint the version.
jin --helpPrint the usage text.

Every pipeline stage is available on its own, so you can watch a program being translated one layer at a time: source text, tokens, syntax tree, checked program, bytecode, result.

Note. -v and version both print the version, and -h and help both print the usage text. A file named help or version in the current folder would be shadowed by those words, so give it a path such as jin ./version.

run

jin run [file|folder] [args]
jin <file.jin> [args]

run type-checks the program, compiles it to bytecode, and executes it on the stack virtual machine. The bare jin <file.jin> form does exactly the same thing.

Given hello.jin:

let who = args()
if len(who) == 0 {
    print("hello, world")
} else {
    print("hello, {who[0]}")
}
$ jin hello.jin
hello, world
$ jin hello.jin Ada
hello, Ada
$ jin run hello.jin Ada
hello, Ada

A program with a type error never starts. run checks first, reports every problem at once, and stops.

$ jin run badtypes.jin
jin: badtypes.jin has type errors:
  8:11: argument 2: cannot use str where int is expected
$ echo $?
1

Note. A file that does not exist is reported as exactly that:

$ jin missing.jin
jin: there is no missing.jin
$ echo $?
1

Program arguments

Anything after the file name is handed to the program, where args() returns it as an array of strings. Jin itself has no options, so there is nothing for the arguments to be confused with.

$ jin hello.jin Ada Bo
hello, Ada

A -- before the arguments is allowed and ignored. It is there for the case where an argument looks like something Jin might want, so that --help reaches the program rather than Jin:

$ jin run hello.jin -- --help
hello, --help

The separator is optional once the target has been named, and it is the only way to pass arguments when there is no target — because then the first word would otherwise be taken for a file name.

$ cd hello
$ jin -- Jin
Hello, Jin!

Careful. The first word after the command is the target, not an argument. In a project folder, jin run Jin looks for a file called Jin and says jin: there is no Jin. Write jin run -- Jin instead.

interpret

jin interpret [file|folder] [args]

interpret runs the program on the tree-walking reference interpreter instead of the bytecode VM. It takes the same file, the same folder and the same arguments, and it prints the same thing.

$ jin interpret hello.jin Ada
hello, Ada
$ echo $?
0

The interpreter is slower — roughly six times slower on a call-heavy program — but it exists so that the two back ends can be checked against each other. The test suite runs every program in the differential corpus on both of them and requires byte-identical output, error text included.

Note. interpret type-checks the program first, exactly as run does. A type error stops it just the same.

check

jin check [file|folder]

check type-checks a program without running it. Nothing is printed by your program, no file is touched, and no side effect happens.

$ jin check hello.jin
hello.jin: no type errors
$ echo $?
0

Every problem is reported at once, each with the line and column it came from:

$ jin check badtypes.jin
jin: badtypes.jin has type errors:
  8:11: argument 2: cannot use str where int is expected
$ echo $?
1

Given a folder that is a project, check type-checks every file the project reaches and says how many there were:

$ jin check hello
hello 0.1.0: no type errors in 2 file(s)

Note. check also catches syntax errors, and reports them the same way run does.

build

jin build [folder]

build checks a whole project and compiles it, then reports what came out. Jin runs from source, so there is no binary to write and no artefact to keep in step with the code — a build here proves the project compiles and tells you how big it is.

$ jin build hello
jin build: hello 0.1.0
  entry: main.jin
  files: main.jin, greeting.jin
  code:  68 bytes of bytecode, 6 constants, 0 locals
  ok
$ echo $?
0

Careful. A folder is only a project when it holds a jin.toml. Pointing build at a folder without one is refused:

$ jin build notes
jin: notes is a folder, but it has no jin.toml, so it is not a project
$ echo $?
1

new

jin new <name>

new writes a starting project into a new folder called <name>.

$ jin new hello
created hello/
  jin.toml
  main.jin
  greeting.jin

next: cd hello && jin run

The name has to be usable as a folder name: letters, digits, - and _. A name that already exists is refused, rather than being written over.

$ jin new "bad name"
jin: "bad name" is not a project name; use letters, digits, - and _
$ jin new hello
jin: hello already exists

The manifest

The project is described by a jin.toml in its folder. Three settings, and that is all of it:

# Settings for this Jin project.
name = "hello"
version = "0.1.0"
entry = "main.jin"
  • name — the project's name, used in messages such as hello 0.1.0. It defaults to the folder's name.
  • version — the project's version, used in the same messages. It defaults to 0.1.0.
  • entry — the file to run. It defaults to main.jin, and it has to be a .jin file inside the project folder.

Lines beginning with # are comments, and blank lines are ignored. An unknown setting is an error, so a typo in the manifest is reported rather than ignored.

Note. jin new writes two files besides the manifest: main.jin, which imports greeting.jin and prints a greeting, and greeting.jin, which holds the hello function. See Projects and Imports for how the two are put together.

Projects

A folder holding a jin.toml is a project. run, interpret, check and build all accept a folder as their target, and they load the entry file together with everything that file imports.

$ jin run hello
Hello, world!
$ jin run hello Ada
Hello, Ada!
$ jin interpret hello Ada
Hello, Ada!

The commands also work from any folder inside a project, the way a build tool does. Jin walks up from the current folder looking for a jin.toml and uses the first one it finds.

$ cd hello
$ jin run
Hello, world!
$ cd lib
$ jin run
Hello, world!
$ jin check
hello 0.1.0: no type errors in 2 file(s)

Outside a project, the same commands want a file:

$ jin check
jin: no jin.toml here; name a file, or start one with 'jin new'
$ echo $?
1

parse

jin parse <file>

parse prints the syntax tree and stops. Nothing is type-checked and nothing runs.

$ jin parse small.jin
Program
  Let total =
    Int 0
  For i in
    Call
      Ident range
      Int 4
    Block
      Expr
        Assign
          Ident total
          Infix +
            Ident total
            Ident i
  Expr
    Call
      Ident print
      Ident total

Note. A file that does not parse is reported and the command stops:

$ jin parse broken.jin
jin: broken.jin has syntax errors:
  2:1: expected a receiver name, got EOF
$ echo $?
1

Note. parse lists each syntax error on its own line, because it can find several in one pass. The commands that go through the module loader — run, check, build — put the first one on a single line instead.

tokens

jin tokens <file>

tokens prints the raw token stream: the lexer on its own, with the line and column of every token. Strings are shown in quotes.

$ jin tokens small.jin
1:1     let      let
1:5     IDENT    total
1:11    =        =
1:13    INT      0
2:1     for      for
2:5     IDENT    i
2:7     in       in
2:10    IDENT    range
2:15    (        (
2:16    INT      4
2:17    )        )
2:19    {        {
3:5     IDENT    total
3:11    =        =
3:13    IDENT    total
3:19    +        +
3:21    IDENT    i
4:1     }        }
5:1     IDENT    print
5:6     (        (
5:7     IDENT    total
5:12    )        )
6:1     EOF

Every line is the line and column, the kind of token, and the token's own text. A string is shown in quotes, so you can see exactly what the lexer made of it.

$ jin tokens tok.jin
1:1     IDENT    print
1:6     (        (
1:7     STRING   "hi"
1:11    )        )
1:12    EOF

Note. tokens and parse need a file. A folder is not accepted, because there is no single file to read.

Bare jin

jin

With no arguments at all, Jin does one of two things, depending on where you are.

Inside a project, it runs that project's entry file:

$ cd hello
$ jin
Hello, world!
$ echo $?
0

Anywhere else, it starts the REPL. The prompt is jin>, state carries from one line to the next, and a half-typed block is held until it parses, so a function can be typed over several lines.

$ jin
Jin 0.10.0 (stage 10: input, functional built-ins, multi-line strings, named records)
Type Jin code and press Enter. 'exit' or Ctrl+D quits.
'clear' discards a half-typed block.
jin> 5
jin> 10
jin>

The three lines typed were let x = 5, print(x * 2) and exit. The REPL shows the value of a declaration, so 5 appears after the first prompt; the 10 is the program's own output, written after the second prompt.

Note. A type error in the REPL is shown and the prompt carries on, so one bad line does not end the session. exit or Ctrl+D quits, and clear throws away a half-typed block.

--version and --help

jin --version
jin -v
jin version
$ jin --version
Jin 0.10.0 (stage 10: input, functional built-ins, multi-line strings, named records)
$ echo $?
0
jin --help
jin -h
jin help
$ jin --help
Jin - a small fast language

Usage:
  jin                       run the project here, or start the REPL
  jin <file.jin> [args]     run a program
  jin run [file|folder] [args]
                            run a program or a project
  jin check [file|folder]   type-check without running
  jin build [folder]        check and compile a whole project
  jin compile <file>        print the bytecode instead of running
  jin interpret <file>      run with the tree-walking interpreter
  jin parse <file>          print the syntax tree instead of running
  jin tokens <file>         print the raw token stream
  jin new <name>            start a project in <name>/
  jin --version             print the version

A folder is a project when it holds a jin.toml. Anything after the file name is
passed to the program, where args() returns it:

  jin greet.jin hello world

Exit codes

There are two, and nothing else.

CodeWhen
0The command did what it was asked to.
1Something went wrong: a type error, a syntax error, a runtime error, a file that is not there, a folder that is not a project, or a project name that cannot be used.

Problems are written to standard error and the message starts with jin:, so a script can tell them apart from your program's own output.

$ jin hello.jin Ada
hello, Ada
$ echo $?
0
$ jin missing.jin
jin: there is no missing.jin
$ echo $?
1

Note. An uncaught runtime error stops the program with exit code 1 as well. A caught one does not: the program carries on and finishes normally.
